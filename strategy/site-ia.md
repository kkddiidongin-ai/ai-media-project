## 1. 권고 IA 모델

### 1-1. 모델 비교

| 모델 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 카테고리가 메인 메뉴, 과제는 내부 탐색 | 일 / 가게·1인 사업 / 생활 / AI 바로 알기 | 이해하기 쉽고 메뉴가 4개로 짧다 | **평범한 블로그 구조**라 "과제 중심" 정체성이 안 보인다. "AI 바로 알기"가 메뉴로 올라와 팁 블로그 인상을 준다 |
| B. 과제가 메인 메뉴, 카테고리는 필터 | 회의·보고 / 업무 글쓰기 / 고객 응대 / … | 정체성이 가장 선명하다 | 과제가 6~8개라 **모바일 메뉴가 길어진다.** 과제가 늘면 메뉴가 계속 바뀐다 |
| C. 메인 메뉴 최소화, 홈에서 과제 탐색 | 메뉴 2~3개, 과제는 홈 섹션에서만 | 단순하다 | 기사로 바로 들어온 사람(검색·공유 유입)은 과제 목록을 찾기 어렵다 |
| **D. 과제 목록 페이지를 입구로, 카테고리는 그 페이지의 묶음 제목으로 (권고)** | 메뉴는 4개 이하. 그중 첫째가 **"과제로 찾기"**. 과제 목록 페이지 안에서 과제들을 일 / 가게·1인 사업 / 생활 / AI 바로 알기로 **묶어 보여줌** | 과제 중심이 메뉴 첫 칸에서 드러난다. 메뉴는 짧게 유지된다. 카테고리는 사라지지 않고 **과제의 묶음 이름**으로 쓰인다. 과제가 늘어도 메뉴는 그대로다 | 과제 허브 1개당 글이 적은 초기에는 허브가 비어 보일 위험이 있다(§19에서 대응) |

### 1-2. 권고: 모델 D

```
메인 메뉴:  과제로 찾기 | 이번 주 | 확인 기록 | 방법
            (검색은 콘텐츠 100편 전후에 추가)
```

- **도구(ChatGPT, Gemini 등)는 메뉴에 두지 않는다.** 글의 메타데이터로만 쓰고, 필터는 콘텐츠 100편 이후에 추가한다(§12).
- **카테고리는 페이지가 아니라 묶음 제목**이다. 과제 목록에서 과제들을 묶는 이름으로만 쓴다. 카테고리 이름이 바뀌어도 URL이 바뀌지 않는다(§14).
- "AI 바로 알기"는 과제 묶음이 된다: AI 답 확인하기 / AI 고르기·비용 / AI 기초(개인정보, 틀리는 이유 등).

## 2. MVP Sitemap (오픈 시점)

| 페이지 | 필수 여부 | 역할 |
|---|---|---|
| 홈 | **필수** | 정체성, 과제 입구, 이번 주, 최근 확인, 진행 중 실험 |
| 과제로 찾기 (과제 목록) | **필수** | 카테고리 묶음별 과제 목록 |
| 과제 허브 × 4 | **필수** | 글이 3편 이상 모인 과제만 개설. 오픈 시: 회의·보고 / 업무 글쓰기 / AI 답 확인하기 / 가게 응대·홍보(임시 통합) (§19) |
| 글 페이지 | **필수** | TEST, TRACK, CHECK, BRIEF, GUIDE 공통 구조 + 형식별 차이 |
| 이번 주 (주간 노트 목록 + 각 호) | **필수** | 재방문 슬롯 |
| 확인 기록 | **필수 (단순 버전)** | 진행 중 / 최근 확인 / 기대 미달 / 업데이트 목록 (§9) |
| 방법 | **필수** | 확인 수준, 측정 방법, 판정 기준, 라벨, AI 사용 원칙, 이해관계 정책 (= 40번 글 + 편집 정책 요약) |
| 소개 | **필수 (짧게)** | 사이트 소개, 운영자 소개(사실만), 연락처 |
| 정정 기록 | 필수 (페이지가 비어 있어도 존재) | 틀리면 고친다는 약속의 증거. 확인 기록 안의 한 섹션으로 둬도 됨 |
| 오류 제보·질문 창구 | 필수 (최소 형태) | 이메일 링크 또는 간단한 양식. 정정의 원천 |
| 개인정보처리방침 | 수집 기능이 있으면 필수 | 양식으로 이메일을 받으면 필요 |
| 카테고리별 목록 페이지 | **불필요** | 과제 목록 페이지의 묶음으로 대체 |
| 도구별 페이지 | **불필요** | 도구 중심 인상을 준다 |
| 전체 최신 글 목록 | 불필요 (확인 기록과 홈으로 대체) | - |
| 검색 결과 페이지 | 불필요 (초기) | 콘텐츠 100편 전후 |
| 교육·강연 페이지 | 불필요 (초기) | 소개 페이지의 한 섹션으로 충분 (§16) |
| 뉴스레터 구독 페이지 | 불필요 (초기) | 채널 미정 (Phase 2 P3) |

```
/
├─ /tasks/                   과제로 찾기
│   ├─ /tasks/meetings/      과제 허브 (예시)
│   └─ …
├─ /a/{slug}/                글 (형식 무관 공통 경로)
├─ /weekly/                  이번 주 (최신 호 + 지난 호)
│   └─ /weekly/{yyyy}-w{ww}/
├─ /record/                  확인 기록 (정정 기록 섹션 포함)
├─ /method/                  방법 (+ /method/editorial/ 편집 원칙)
└─ /about/                   소개 (연락, 기관·교육 문의 텍스트 링크)
```

| 층 | 항목 | 비고 |
|---|---|---|
| **Main (헤더, 4개 이하)** | 과제로 찾기 / 이번 주 / 확인 기록 / 방법 | 모바일에서는 헤더에 로고 + "과제로 찾기" + 메뉴 버튼. 나머지는 메뉴 안에 |
| **Secondary (푸터)** | 소개, 편집 원칙, 정정 기록, 이해관계 정책, 오류 제보, 기관·교육 문의, 개인정보처리방침 | 신뢰 정보를 푸터에서 언제든 찾을 수 있게 |

| **필터 (나중에)** | 형식, 판정, 확인 수준, 효과 태그, 도구 | §12 단계에 따라 |
| **랜딩 페이지** | 과제 허브, 주간 노트 각 호, 방법 | 외부에서 링크하기 좋은 페이지 |

## 5. Homepage 구조

**5~10초 안에 이해시켜야 할 것**: ① 여기는 AI를 **직접 해보고 확인한 결과**를 보여주는 곳이다 ② 도구가 아니라 **내가 하려는 일**로 찾는다 ③ 실패와 업데이트까지 기록한다 ④ 시작점은 여기다

**넣지 않는 섹션**: 많이 보는 콘텐츠(초기에는 데이터가 없음), 최근 글 전체 목록, 뉴스 속보, 교육 신청, 구독 폼, 도구 로고 나열

```
HEADER
  로고(미정) · 과제로 찾기 · [메뉴]           ← CTA 버튼 없음
↓
HERO (모바일 첫 화면의 절반 이하)
↓
① 과제로 찾기
↓
② 이번 주
↓
③ 최근 확인한 것
↓
④ 진행 중인 실험
↓
⑤ 처음이라면
↓
(⑥ 업데이트된 글: 3건 이상 쌓이면 노출)
↓
FOOTER
```

| 섹션 | 목적 | 보여줄 내용 | 왜 이 위치인가 | 기대 행동 |
|---|---|---|---|---|
| **HERO** | 정체성 한 번에 전달 | 한 문장 정의(가칭, 예: "AI, 해본 만큼만 말합니다" 류의 원칙형 문장) + 짧은 보조 문장 1줄("일과 생활에서 직접 확인한 시간·비용·실패를 기록합니다") + 텍스트 링크 "어떻게 확인하나요?" → 방법 | 가장 먼저 "무엇이 다른가"를 말해야 한다. 크게 주장하지 않고 원칙만 말한다 | 스크롤하거나 방법 링크 클릭 |
| **① 과제로 찾기** | "나와 관련 있나?"에 바로 답함 | 과제 버튼 6개 안팎, 묶음 제목(일 / 가게·1인 사업 / 생활 / AI 바로 알기)과 함께. 각 과제에 확인한 글 수 표시(실제 수, 0이면 표시하지 않음) | 정체성 다음으로 중요한 것이 자기 선택이다. 과제 중심을 첫 섹션에서 보여준다 | 과제 허브로 이동 |
| **② 이번 주** | 습관 슬롯, 최신성 | 최신 주간 노트의 "해볼 것 하나" 1줄 + "진행 중 실험" 1줄 + 호 번호·날짜 + "이번 주 노트 보기" | 재방문자는 이것을 보러 온다. 신규 방문자에게는 "매주 갱신되는 곳"이라는 신호다 | 주간 노트로 이동 |
| **③ 최근 확인한 것** | 직접 확인한다는 증거 | 결과 카드 3~4개 (판정, 확인 수준, 확인일) | 주장이 아니라 실물로 증명한다 | 글 읽기 |
| **④ 진행 중인 실험** | "다음 결과"라는 재방문 이유 | 추적 카드 1~2개 (○일째, 다음 업데이트 날짜) | ③ 다음에 두어 "끝나지 않은 이야기"를 보여준다 | 추적 글 읽기, 다시 오기 |
| **⑤ 처음이라면** | 첫 방문자의 시작점 | 엄선 3편: 질문 바꾸기 실험(32), 네이버 AI 요약 대조(41), 방법(40) | 스크롤을 끝까지 내린 첫 방문자를 위한 안내. 상단에 두면 재방문자에게 방해가 된다 | 연속 읽기 시작 |
| **⑥ 업데이트된 글** (조건부) | 계속 확인한다는 증거 | 최근 업데이트·재검증 2~3건 (무엇이 바뀌었나 한 줄) | 기록이 3건 이상 쌓이기 전에는 비어 보이므로 숨긴다 | 글 다시 읽기 |
| **FOOTER** | 신뢰 정보와 부가 링크 | 소개, 방법, 편집 원칙, 정정 기록, 이해관계 정책, 오류 제보, 기관·교육 문의(텍스트 링크) | 필요한 사람이 언제든 찾을 수 있게 | - |

## 6. Article Page 구조 (모바일 기준)

### 6-1. 첫 화면 (모바일 한 화면 안)

```
[과제 경로]  과제로 찾기 › 회의·보고
[형식 라벨]  직접 실험 (가칭)
[제목]
[한 줄 요약]  무엇을 해봤고, 결론의 방향이 무엇인지 한 문장
[판정 줄]    판정 배지 · 확인 수준 · 확인일           ← 한 줄
[핵심 결과]  최대 3줄 (예: 시간 / 비용 / 한계 한 줄)    ← 측정한 것만
[이해관계]   제휴·협찬·무상 제공이 있을 때만 한 줄       ← 있으면 반드시 첫 화면 (편집 정책 M1)
```

**첫 화면에 넣지 않는 것**: 도구·버전·요금제, 테스트 조건, 결제 여부 → 아래 "실험 정보" 접힘 영역으로 보낸다.

### 6-2. 본문 순서

| 순서 | 블록 | 모바일 처리 |
|---|---|---|
| 1 | 첫 화면 (§6-1) | 고정 순서 |
| 2 | **실험 정보** (도구·모델·버전·요금제, 결제 여부, 사용 자료가 가상인지, 조건) | **접힘** (한 줄 요약: "○○ 무료 / 2026-10 / 가상 자료") |
| 3 | 어떤 문제였나 → 기존에는 어떻게 했나 | 짧은 문단 |
| 4 | 어떻게 해봤나 → 실제 과정 (대표 스크린샷) | 이미지는 세로로, 확대 가능 |
| 5 | **측정 결과** | 넓은 표 금지. **세로 카드형 키-값 목록**(기준 → AI 사용 → 차이) |
| 6 | 실패·고친 부분 | 목록 |
| 7 | 누구에게 맞나 / 안 맞나 | 두 개의 짧은 목록 |
| 8 | **혼자 해보려면** | 번호 단계 (복사 가능한 입력 예시는 접힘 가능) |
| 9 | 한계 | 짧게 (n=1, 운영자 조건, 도구 변경 가능성) |
| 10 | 다음에 확인할 것 (남은 질문) | 1~3줄. 과제 허브의 "아직 확인하지 못한 것"과 연결 |
| 11 | **이어 읽기** (최대 3개, 각각 이유 한 문장) | 카드 대신 텍스트 링크 + 이유 |
| 12 | 과제 허브로 돌아가기 | 한 줄 링크 |
| 13 | 버전 기록 | **접힘.** 판정이 바뀐 경우에만 첫 화면 위에 한 줄 공지 |
| 14 | 이 글의 제작에 AI를 쓴 부분 · 증거 공개 범위 · 오류 제보 | 작은 글씨 한 블록 |

### 6-3. 형식별 차이

| 형식 | 첫 화면의 차이 | 본문의 차이 |
|---|---|---|
| TRACK | 판정 줄 대신 **진행 상태 줄**: "진행 중 · ○일째 / 30일 · 다음 업데이트 ○월 ○일" | 사전 설계(기간, 중단 기준) 블록, 날짜별 기록은 접힘, 최종 결과 블록은 완료 후 상단으로 |
| CHECK | 제목 아래 **주장 박스**: "주장: … (원출처, 확인일)" → 그다음 판정 줄 | 주장의 조건 → 실행 여부(실험 안 함이면 이유) → 결과 (매출·순이익 구분) → **누구에게는 통할 수 있나** |
| BRIEF | 판정 대신 "써볼까 / 넘길까" 한 줄 | 800~1,500자. 영향을 받는 과제 허브 링크 |
| GUIDE | 판정 없음. 확인 수준 + 마지막 점검일 | 근거가 된 사이트 안의 글 목록 |

## 7. Content Card 구조

**썸네일 원칙**: 장식용 이미지나 AI 생성 이미지는 쓰지 않는다. 실제 스크린샷 일부를 쓰거나 이미지 없이 운영한다. 읽기 시간과 카테고리는 카드에 표시하지 않는다(과제 라벨이 대신한다). 도구 이름은 카드에 쓰지 않는다.

| 카드 | 쓰는 곳 | 보여줄 것 (위에서 아래로) | 배지 최대 |
|---|---|---|---|
| **결과 카드** (TEST, CHECK, 완료된 TRACK) | 홈 ③, 과제 허브, 확인 기록 | 과제 라벨 · 제목 · **판정 배지 + 측정값 1개**(측정한 경우만) · 확인 수준 · 확인일 | 2개 (판정, 확인 수준) |
| **추적 카드** (진행 중 TRACK) | 홈 ④, 과제 허브 | 과제 라벨 · 제목 · **"○일째 / ○일"** · 다음 업데이트 날짜 | 1개 (진행 중) |
| **기본 카드** (BRIEF, GUIDE, 주간 노트) | 과제 허브, 주간 노트 | 과제 라벨(있으면) · 제목 · 한 줄 요약 · 확인일(또는 발행일) | 0~1개 |

- 카드 종류를 3개 이상으로 늘리지 않는다.
- "업데이트됨"은 최근 30일 안에 업데이트된 경우에만 날짜 옆에 작은 글씨로 붙인다.

### 8-2. 장기 자산으로서의 가치

**가장 강한 자산이 될 수 있다고 판단한다** [INFERENCE].
- **살아 있는 요약**: 블록 2는 글이 쌓이고 재검증될수록 정확해진다. 개별 글이 낡아도 허브는 "현재 기준"을 보여준다.

## 10. Record / Lab Page 판단

**필요하다.** 다만 "우리가 이만큼 연구했다"는 자기 홍보 페이지가 아니라 **독자가 쓰는 목록 페이지**로 만든다.

- **독자에게 주는 가치**: "지금 무엇이 확인 중인가", "최근에 무엇이 바뀌었나", "어디서 기대에 못 미쳤나"를 한 곳에서 본다. 재방문자가 새로 확인된 것만 빠르게 훑는 페이지다.
- **운영자에게 주는 가치**: 강의 자기소개에서 보여줄 증거가 된다(positioning §12). 이는 결과적인 효과이지, 페이지의 목적이 아니다.

**MVP 구조 (단순 목록, 자동 통계 없음)**

| 섹션 | 내용 |
|---|---|
| 진행 중 | 추적 카드 |
| 최근 확인 | 결과 카드, 최종 확인일 순 |
| 기대 미달·중단 | 해당 결과만 |
| 최근 업데이트·재검증 | 무엇이 바뀌었나 한 줄 |
| 정정 기록 | 날짜, 글, 무엇이 틀렸고 어떻게 고쳤나 |

- **초기에는 총계 숫자를 크게 보여주지 않는다.** 숫자가 작을 때 강조하면 약점이 드러나고, 숫자를 강조하는 순간 허영 지표가 된다. 섹션별 목록만 보여준다.
- 누적 지표(실험 수, 실패 비율 등)는 Growth 단계에서, 목록과 연결된 숫자로만 추가한다(architecture §9-2 원칙).
- 이름은 가칭("확인 기록")이다. "연구실", "Lab"처럼 운영자를 과시하는 이름은 피한다.

## 11. Weekly Page

**웹 콘텐츠로서의 역할**: 주간 노트는 사이트의 **"이번 주 표지"**다. 새 원고가 아니라 그 주의 엔진 결과물을 엮은 편집물이다(media-engine §12-1).

| 페이지 | 구조 |
|---|---|
| `/weekly/` (목록) | 상단: 최신 호 전체 / 아래: 지난 호 목록 (호 번호, 날짜, 그 주의 "해볼 것" 한 줄) / 안내 한 줄: "매주 ○요일 이 페이지에 올라옵니다" (요일은 운영 결정) |
| `/weekly/{yyyy}-w{ww}/` (각 호) | 이번 주 바뀐 것 → 이번 주 직접 확인한 것 → **해볼 것 하나** → 진행 중 실험 → 업데이트된 이전 글 → 이전 호 / 다음 호 링크 |

- **구독 기능은 없다.** 발송 채널은 Phase 2 P3 검증 후에 정한다. 대신 각 호의 URL을 안정적으로 유지해 나중에 발송 채널과 연결할 수 있게 한다.
- "해볼 것 하나"는 원본 글의 "혼자 해보려면"으로 링크한다. 과제를 해본 사람이 원본 글로 돌아가는 흐름을 만든다.

| 도구 | ✓ (글 안 실험 정보에서만) | ✓ | ✗ | ✓ (100편~) | 고정 목록. **실제로 과제를 수행한 도구만** 기록 |
| 확인일 (최초·최종) | ✓ | ✓ | ✗ | 정렬 | - |
| Freshness | ✗ (대신 "확인한 지 ○개월" 표시) | ✓ | ✗ | ✗ | FAST / MEDIUM / SLOW |
| 상태 | 일부만 ✓ (진행 중, 업데이트됨, 재검증 필요) | ✓ | ✗ | ✓ (확인 기록 탭) | 6개 (media-engine §8) |
| 다음 점검일 | ✗ | ✓ | ✗ | ✗ | - |

**태그 증식 방지 규칙**
1. **자유 태그를 쓰지 않는다.** 모든 필드는 고정 목록이다.
2. **새 과제는** 글이 3편 이상 있거나 2개월 안에 3편 이상 예정일 때만 추가한다. 과제는 초기 6~8개, 상한 12개(초과하면 하위 과제로 나눈다).
3. 도구 목록은 실제 TEST에 쓴 도구만 추가한다. 한 번 열어본 도구는 추가하지 않는다.
4. 분기마다 한 번, 쓰이지 않는 값을 정리한다(월간 결산 내부 메모).

## 14. URL 구조

**원칙**: URL은 **바뀌지 않는 것**만 담는다. 카테고리 이름, 과제 표시 이름, 형식, 판정, 연도, 도구 이름, 결과는 URL에 넣지 않는다(재검증이나 이름 변경 때 URL이 깨지지 않게 하기 위해).

| 페이지 | 경로 | 비고 |
|---|---|---|
| 홈 | `/` | |
| 과제로 찾기 | `/tasks/` | |
| 과제 허브 | `/tasks/{task-slug}/` | 영문 소문자 slug. 표시 이름(한글)이 바뀌어도 slug 유지. 하위 과제도 한 단계로 (`/tasks/meeting-notes/`), 부모 관계는 메타데이터로 |
| 글 (모든 형식) | `/a/{slug}/` | 형식·카테고리·연도를 넣지 않음. slug는 과제 중심 영문 단어(예: `meeting-summary-three-tools`). **결과·수치·도구 버전을 넣지 않음** |
| 주간 노트 | `/weekly/`, `/weekly/{yyyy}-w{ww}/` | ISO 주차 |
| 월간 결산 | `/monthly/{yyyy}-{mm}/` | SHOULD HAVE 단계 |
| 확인 기록 | `/record/` | 섹션은 앵커로 (`/record/#corrections`) |
| 방법 | `/method/`, `/method/editorial/` | |
| 소개 | `/about/` | |

- 글의 제목이 재검증 후 바뀌어도 slug는 바꾸지 않는다.
- 바꿔야 할 때는 이전 URL에서 새 URL로 영구 리다이렉트를 건다.
- `/a/` 접두어는 가칭이다. 짧고 중립적인 한 글자·한 단어를 권한다.

## 16. Mobile First 핵심 원칙

1. **글 첫 화면 = 제목 + 한 줄 요약 + 판정 줄 1줄 + 핵심 결과 최대 3줄.** 메타정보는 접는다. 예외는 이해관계 표시(있으면 첫 화면).
2. **넓은 표를 쓰지 않는다.** 측정 결과, 허브의 요약, 비교는 세로 키-값 목록이나 짧은 목록으로 바꾼다. 표가 꼭 필요하면 3열 이하로.
3. **헤더는 로고 + 과제로 찾기 + 메뉴 버튼.** 메인 메뉴는 4개 이하.
4. **카드는 3줄 안팎, 배지는 최대 2개.** 도구 이름, 카테고리, 읽기 시간을 카드에 넣지 않는다.
5. **필터는 초기에 없다.** 도입할 때도 가로 탭 한 줄(최대 4개)로 시작한다.
6. **긴 설계 정보(실험 조건, 날짜별 기록, 버전 기록)는 기본적으로 접는다.**
7. **스크린샷은 세로로 자르고 확대할 수 있게 한다.** 결과를 읽을 수 없는 축소 이미지는 쓰지 않는다.
8. **공유 단위를 고려한다.** 카톡 공유 미리보기에 보일 제목과 한 줄 요약이 그 자체로 이해되어야 한다(요약에 판정 방향을 포함).

## 18. 회원 기능 판단

**결론: 오픈 시점에는 회원 기능을 넣지 않는다.** "콘텐츠 가치와 재방문 이유를 먼저 검증한다"는 가설을 지지한다.

| 기능 | 판단 | 이유 |
|---|---|---|
| 회원가입·로그인 | 넣지 않음 | 재방문 이유가 검증되지 않았다. 개인정보 처리 부담이 1인에게 크다 |
| 북마크·저장 | 넣지 않음 | 브라우저 북마크와 카톡 공유로 대체된다 |
| 댓글 | **넣지 않음** | 관리·신고 대응 부담, 광고성 댓글 위험. 대신 **오류 제보·질문 창구(이메일·양식)**를 둔다. 이 창구는 정정과 독자 질문 소스로 쓰인다 |
| 개인화 | 넣지 않음 | 콘텐츠 수가 적다 |
| 유료 회원 | 넣지 않음 | Phase 5 이후 별도 판단 |
| 구독 (이메일 등) | **보류** (결정 필요) | Phase 2 P3 검증 전이다. 다만 재방문 측정을 위해 가벼운 "주간 노트 알림 신청"을 둘지는 운영자가 결정할 사항이다. 두면 개인정보처리방침이 필요하다 |

**나중에 추가하기 쉽게 지금 지켜둘 것**
- 모든 글과 주간 노트에 **바뀌지 않는 ID와 URL**
- 과제, 도구, 효과 태그를 **고정 목록**으로 관리 → 나중에 "관심 과제 알림", "저장한 과제의 업데이트 알림"을 만들 수 있다
- 버전 기록을 구조화된 필드로 관리 → 나중에 "내가 본 글이 재검증되면 알림"이 가능하다
- 주간 노트 각 호를 독립된 페이지로 → 나중에 이메일 발송 본문으로 재사용한다
