## 1. Media Engine 전체 구조

**하나의 글이 끝나는 곳에서 다음 글의 재료가 나오는 순환 구조**를 만든다.

```
        ┌──────────────────────── ⑧ 새 질문·실패·재검증 필요 ─────────────────────┐
        ▼                                                                        │
① 소스(Source) ─→ ② 인박스(Inbox) ─→ ③ 5분 선정(Selection Rule)                  │
                                            │                                    │
                                            ▼                                    │
                          ④ 형식별 파이프라인 (TEST/TRACK/CHECK/BRIEF/GUIDE)       │
                                 │  (모든 실행은 Research Log에 먼저 기록)          │
                                 ▼                                               │
                          ⑤ 발행 + 연결 (Cluster 소속, 이유가 있는 링크 최대 3개)  │
                                 ▼                                               │
                          ⑥ 후속: TRACK 승격 / 다음 단계 / 비교 실험 ──────────────┤
                                 ▼                                               │
                          ⑦ 점검: Freshness(주기 + 이벤트) → 업데이트·재검증 ─────┤
                                 ▼                                               │
                          ⑨ 정기 레이어: 주간 노트 / 월간 결산 (기존 글을 엮음) ────┘
```

**순환을 강제하는 세 가지 규칙**
1. **"남은 질문" 칸**: 모든 TEST·TRACK·CHECK는 발행할 때 "이번에 확인하지 못한 것 / 다음에 해볼 것"을 1~3줄 남긴다. 이 줄은 자동으로 인박스에 들어간다(⑧).
2. **실패는 버려지지 않는다**: 기대 미달 결과는 글, 주간 노트 한 줄, Research Log 중 하나로 반드시 남고, "조건을 바꾸면?"이 인박스로 간다(§13).
3. **점검일이 있는 글**: 모든 발행 글은 "다음 점검일"을 가진다. 점검 결과는 업데이트, 재검증, 보관 중 하나로 이어지고, 재검증은 새 글이나 버전 기록이 된다(§11, §12).

## 2. 콘텐츠 관계 모델 (최소 버전)

제안된 9개 관계 중 **5개만** 쓴다. 나머지는 이 5개로 표현하거나 버전 기록 안에서 처리한다.

| 관계 | 의미 | 독자에게 보이는 "왜 다음 글인가" 문장 예시 | 흡수한 관계 |
|---|---|---|---|
| **과제 소속 (Cluster)** | 이 글이 속한 과제 묶음 | "회의 정리에 관한 다른 확인 결과" | PARENT, RELATED |
| **배경 (Background)** | 이 글을 이해하는 데 필요한 기초 | "AI 요약이 왜 틀리는지 먼저 보려면" | BACKGROUND |
| **비교 (Compare)** | 같은 과제를 다른 방법·도구·조건으로 해본 글 | "같은 회의를 다른 도구로 했을 때" | COMPARE |
| **다음 (Next)** | 이 결과 다음에 이어지는 실험 또는 직접 해볼 단계 | "여기서 할 일 목록까지 뽑아보면" | FOLLOW-UP, NEXT STEP |
| **추적 (Track)** | 이 결과를 장기간 따라가는 TRACK | "30일 동안 계속 써보면 어떻게 되는지" | LONG-TERM |

- **UPDATE, RETEST는 링크가 아니라 버전 기록**으로 처리한다(§12). 같은 글의 이력이기 때문이다. 재검증 결과가 새 글이 되면 원래 글과 서로 "비교" 관계로 잇는다.
- **링크 규칙**
  - 글 끝의 연결은 **최대 3개**
  - 각 링크에는 **"왜 이 글을 다음에 읽어야 하는지" 한 문장이 필수**다
  - 태그만 겹쳐서 연결하는 방식은 쓰지 않는다
  - 연결할 글이 아직 없으면 "다음에 확인할 것"으로 예고한다(예고는 인박스 항목이 된다)

기존 백로그 50개를 과제 기준으로 다시 묶었다. **억지로 전부 넣지 않았다.**

### 3-2. Cluster 허브

각 Cluster는 **허브 페이지 1개**를 가진다. 허브는 새로 쓰는 글이 아니라 목록과 요약이다.
- 이 과제에서 지금까지 확인한 것 (판정 요약, 확인일)
- 진행 중인 추적
- 아직 확인하지 못한 것 (= 인박스 항목 공개. 독자에게는 "예정"으로 보임)
- 배경 글

오픈 시 허브는 4개다 (Phase 5A 승인): **회의·보고 / 업무 글쓰기 / AI 답 확인하기 / 가게 응대·홍보 (C3+C4 임시 통합)**. 임시 허브는 고객 응대와 홍보 문구가 각각 3편이 되면 나눈다(site-ia §19). 독자에게는 "Cluster"라는 말을 쓰지 않고 과제 이름만 보여준다.

### 3-3. 운영자 업무 소스 사용 원칙
- 운영자의 실제 업무는 **과제의 출처**로만 쓴다. 고객, 투숙객, 거래처의 실제 정보는 절대 쓰지 않는다. 데이터는 가상 또는 각색이며, 그 사실을 본문에 밝힌다(편집 정책 P1, P5).
- 운영자의 사업장(예: 숙박업소)을 공개할지는 **운영자가 결정할 사항**이다. 공개하지 않아도 "숙박업 문의 응대"처럼 과제 단위로는 쓸 수 있다.
- 경력의 크기를 표현하지 않는다. "숙박업 문의에 매일 답하는 입장에서 확인했다"처럼 **사실 그대로의 맥락**만 쓴다.

## 4. Content Journey (6개)

교육 판매 Funnel이 아니라, 독자가 다음 글로 움직이는 이유를 설계한다.

| # | Journey | Entry | Second Read | Third Read | Return Trigger |
|---|---|---|---|---|---|
| J1 | **업무 과제 검색** | 1 회의 정리 TEST (검색·공유) | 9 업무보고 30일 TRACK (진행 중) | C1 허브 (예정 항목 확인) | **TRACK 다음 업데이트 날짜** |
| J2 | **AI 변화 → 내 일** | 41 네이버 AI 요약 BRIEF | 22 행정 서류 대조 TEST | 46 틀리는 이유 GUIDE (배경) | 주간 노트의 "이번 주 확인한 것" |
| J3 | **가게 사장님 공유** | 13 메뉴 문구 외주 vs AI | 12 리뷰 답글 30개 | 18 유료 AI 한 달 TRACK (오픈 후 시작) | **30일 "구독료 본전" 결과** |
| J4 | **써보고 멈춘 사람** (지인·교육 공유) | 32 질문 바꿔서 다시 시켜보기 | 2 이메일 10통 | 주간 노트의 "해볼 것 하나" | **매주 같은 요일의 과제 하나** |
| J5 | **수익 광고를 본 사람** (오픈 4주 후부터) | 34 전자책 수익 주장 CHECK | 39 판매 페이지 읽는 법 GUIDE | 45 YouTube 정책 BRIEF | 새 CHECK, 월간 결산의 "이번 달 확인한 주장" |
| J6 | **강의·교육 현장** | 강의 주제와 같은 과제의 TEST | 같은 Cluster의 다른 글 | 40 방법론 | 주간 노트 (교육 후 연습 과제) |

모든 Journey는 **방법론(40)이나 Cluster 허브**를 한 번은 지나가게 한다. 사이트의 존재 이유를 이해시키는 장치다.

## 5. Source System (콘텐츠 아이디어 공급원)

| 소스 | 우선순위 | 이유 | 주의 |
|---|---|---|---|
| **운영자의 실제 업무** (영업, 고객상담, 숙박업, 홈페이지 제작, 업무관리) | **HIGH** | 매주 새로 생기고, 과제 중심이며, 직접 확인할 수 있고, 다른 곳이 복제할 수 없다 | 고객 정보 금지, 가상·각색 데이터 |
| **기존 글의 "남은 질문"** | **HIGH** | 비용이 들지 않고 연결 구조를 자동으로 만든다 | 한 주제에 너무 파고들지 않도록 Cluster 균형 확인 |
| **실패·기대 미달 결과** | **HIGH** | "조건을 바꾸면?"이 바로 다음 실험이 된다 | 실패를 억지로 만들지 않는다 |
| **예정된 재검증** (점검일 도래) | MEDIUM~HIGH | 연구 이력의 핵심. 결과가 바뀌면 콘텐츠가 된다 | 월 업데이트 시간 상한 안에서만 |
| 주요 AI 서비스 업데이트 | MEDIUM | 시의성 | **"어느 Cluster의 과제에 영향을 주나?"**를 통과한 것만. 통과 못 하면 주간 노트 한 줄이나 버림 |
| AI 광고·홍보·수익 주장 | MEDIUM | "무엇을 믿어도 되나" 가치 | 수익 주장은 월 1편 이하, 저격 금지 |
| 운영자의 생활 문제 | MEDIUM | 생활 카테고리 공급 | 가족 참여는 동의 필요 |
| 요금제·정책 변화 | MEDIUM | 주로 **기존 글의 업데이트 트리거**로 쓰고, 새 글은 드물게 | FAST 점검과 연결 |
| 교육 현장의 질문 | MEDIUM (강의 발생 후 HIGH) | 실제 사람의 문제 | 수강생 정보 비공개 |
| 커뮤니티·댓글 반복 질문 | MEDIUM~LOW | 공개 게시물에서 문제 패턴 발견 | 개인 게시물을 인용할 때는 비식별 처리 |
| 독자 질문·검증 요청 | LOW → (오픈 3개월 후) HIGH | 초기에는 독자가 없음 | 접수 창구는 나중에 연다 |
| 검색 유입 질문 | LOW → (데이터가 쌓인 뒤) MEDIUM | 초기에는 데이터 없음. AI 요약이 검색 유입을 줄이는 중(Phase 1) | - |
| 새로운 AI 도구 | LOW | 도구 중심으로 흐를 위험 | 기존 Cluster의 과제에 써볼 때만 |

**인박스 운영**: 소스를 가리지 않고 한 곳(스프레드시트나 메모 한 개)에 넣는다. 항목마다 `출처 소스 / 관련 Cluster / 한 줄 과제 설명`만 적는다. 인박스 정리는 주 1회 15~30분이다.

## 6. Idea → Publish Pipeline

### 6-1. 공통 뼈대 (모든 형식)
`인박스 → 선정(5분) → 설계 → 실행 (Research Log 기록) → 작성 → 점검(사실·개인정보·이해관계) → 발행·연결 → 후속(남은 질문, 점검일 설정)`

### 6-2. 형식별 차이

| 형식 | 설계 | 실행 | 작성 | 점검 | 발행 후 | 예상 시간 |
|---|---|---|---|---|---|---|
| **TEST** | 과제, 기준선, 성공 기준을 **사전 기록** (20~40분) | 실행 + 시간·비용 기록 + 스크린샷 (2~5시간) | 표준 틀 10단계 (2~3시간) | 사실, 개인정보 가림, 이해관계 (30~60분) | 남은 질문 → 인박스, 점검일 설정 (MEDIUM) | 4~10시간 |
| **TRACK** | 기간, 기록 방법, **중단 기준**까지 사전 공개 (1~2시간) | 매일·매주 기록 (주 30분~2시간) | 시작 글 → 중간 업데이트 → 최종 글 | 최종 글에서 한 번 더 | 90일·6개월 재방문 일정 | 기간 전체 6~15시간 (나눠서) |
| **CHECK** | 원출처 추적, 주장 조건 정리, **실행 가능 여부 판단** (TEST 또는 NOT TESTED) | 실행 가능한 부분만 | 주장 → 조건 → 결과 → **누구에게는 통하는지** | **톤·저격 점검 (R12)**, 법적 표현 | 새 주장 등장 시 링크 | 5~10시간 |
| **BRIEF** | **"어느 Cluster의 과제에 영향을 주나?"** 통과 여부 (5분) | 직접 사용 30~60분 | 800~1,500자 | 확인일, 출처 | FAST 점검 (30~60일) | 1~3시간 |
| **GUIDE** | 사이트 안의 근거 글 모으기 | (보통 없음) | 3~5시간 | 출처와 확인일 | SLOW 점검 (6~12개월) | 3~6시간 |

**Research Log가 모든 형식의 0단계**다. 발행하지 않는 실행도 먼저 로그에 남긴다(§16).

## 7. Editorial Selection Rule (5분 판단)

12개 기준을 점수화하지 않는다. **관문 3개 + 우선순위 질문 3개**로 끝낸다.

### 관문 (하나라도 "아니오"면 이번 주에는 하지 않음)
1. **과제 문장**: "누가, 어떤 일을 할 때, 무엇이 문제인가"를 한 문장으로 말할 수 있는가?
2. **확인 가능성**: 이번 주기 안에 직접 확인(실측 또는 직접 사용)할 수 있는가? 안 된다면 확인 수준을 "출처 확인"으로 낮춰서 정직하게 쓸 수 있는가?
3. **안전**: 개인정보·고객정보 없이, 편집 정책을 어기지 않고 할 수 있는가?

### 우선순위 (관문을 통과한 것 중에서)
- **A. 연결**: 기존 Cluster를 키우거나, 진행 중인 글·TRACK과 이어지는가?
- **B. 출처**: 운영자의 실제 업무나 생활에서 나온 문제인가?
- **C. 크기**: 이번 주 슬롯(직접 실행형 1편 + 가벼운 1편)에 맞는 크기인가? HIGH 난이도는 2주에 1편까지만.

→ A·B·C 중 두 개 이상이면 이번 주, 하나면 다음 주 후보, 없으면 인박스에 둔다.

**균형 점검은 글마다가 아니라 월 1회** 월간 결산 때 한다. Cluster 편중, 카테고리 편중, 수익 주장 비중, 실패 공개 여부를 본다.

## 8. 콘텐츠 상태 관리 (최소 6개)

| 상태 | 의미 | 다음 상태 |
|---|---|---|
| **아이디어** | 인박스에 있음 | 진행 중 / (삭제) |
| **진행 중** | 설계, 실행, 작성 단계 (세부 단계는 체크리스트로만 관리) | 발행 / 아이디어로 되돌림 / Research Log로만 남김 |
| **발행** | 공개됨. **다음 점검일**이 있음 | 추적 중 / 점검 필요 |
| **추적 중** | TRACK 진행 중. 다음 업데이트 날짜 있음 | 발행(최종) |
| **점검 필요** | 점검일 도래 또는 이벤트 발생 | 발행(확인만) / 발행(업데이트됨) / 재검증 → 발행 / 보관 |
| **보관** | 도구 종료, 과제 소멸. 페이지는 남기되 안내문 표시 | - |

모든 발행 글의 필수 관리 필드: `ID, 형식, Cluster, 카테고리, 확인 수준, 최초 확인일, 최종 확인일, Freshness 등급, 다음 점검일, 상태`

ID 규칙(제안): `형식 약자-연도-일련번호` (예: T-2026-001, K-2026-003). 증거 폴더와 Research Log가 같은 ID를 쓴다.

## 9. Freshness / Update System

### 9-1. Freshness 등급

| 등급 | 대상 | 정기 점검 주기 | 오래됐다는 표시 |
|---|---|---|---|
| **FAST** | 기능·요금·무료 한도·정책을 다루는 글, BRIEF 대부분 | 30~60일 | 최종 확인 후 60일이 지나면 "확인한 지 ○개월" 표시 |
| **MEDIUM** | 도구로 과제를 수행한 TEST, 도구 비교, 사용 단계가 있는 글 | 90일~6개월 | 6개월 경과 시 표시 |
| **SLOW** | 방법론, 과제 해결 원칙, 안전 기준 GUIDE | 12개월 | 12개월 경과 시 표시 |

### 9-2. 이벤트 트리거 (날짜와 무관하게 "점검 필요"로 전환)

| 이벤트 | 조치 |
|---|---|
| 가격·무료 한도 변경 | FAST 글 업데이트. 비용 비교가 들어간 TEST는 비용 칸만 업데이트 |
| 모델·버전 교체 | 관련 TEST를 "재검증 필요"로 표시. 우선순위를 매겨 재검증 |
| UI 변경으로 따라 하기 단계를 재현할 수 없음 | "혼자 해보려면" 칸 업데이트 (판정은 유지) |
| 정책 변경 (저작권, 수익화, 개인정보) | 관련 CHECK·GUIDE 업데이트 |
| 독자 제보나 운영자 재실행에서 **결과 재현 실패** | 재검증. 판정이 바뀔 수 있음 |
| 도구·서비스 종료 | 보관 + 대체 글 링크 |

### 9-3. 업데이트 수준 구분

| 수준 | 기준 | 표시 |
|---|---|---|
| **확인만** | 다시 봤지만 바뀐 것이 없음 | 최종 확인일만 갱신 |
| **부분 업데이트** | 단계, 가격, 화면이 바뀜. **판정은 그대로** | "업데이트됨 (날짜): 무엇이 바뀌었는지" |
| **재검증** | 과제를 다시 실행하고 다시 측정함 | 재검증 기록. 판정이 바뀌면 상단에 공지 |
| **보관** | 더 이상 유효하지 않음 | 상단 안내 + 대체 글 링크. 삭제하지 않음 |

### 9-4. 업데이트 예산 (1인 운영 핵심)
- **월 업데이트 시간 상한: 4~6시간** (가설). 넘치는 항목은 "재검증 필요" 표시만 하고 다음 달로 넘긴다.
- 우선순위: ① Launch Set과 Journey의 입구 글 ② 판정이 바뀔 가능성이 큰 이벤트 ③ Cluster 허브에 걸린 글 ④ 나머지
- 조회수 데이터가 생기면 우선순위에 반영한다.

## 10. Version History

모든 발행 글의 하단에 **버전 기록 블록**을 둔다. 조용히 덮어쓰지 않는다.

```
[버전 기록]
- 2026-10-xx  최초 확인   (도구/버전/요금제)  판정: 조건부
- 2027-01-xx  부분 업데이트  요금제 변경 반영, 판정 유지
- 2027-01-xx  재검증       같은 과제 재실행, 수정 시간 변화    판정: 조건부 → 쓸 만함
```

- **판정이 바뀐 경우에만** 글 상단에 한 줄로 알린다: "2027-01 재검증 결과 판정이 바뀌었습니다."
- 사이트 전체의 **"판정 변경 로그"**와 **"정정 로그"**가 이 블록들에서 자동으로 모인다. 이 기록 자체가 "계속 확인하는 곳"이라는 가장 강한 증거가 된다.
- 이전 버전의 측정값은 지우지 않고 표에 남긴다(예: 2026년 측정 vs 2027년 측정).

## 11. 실패 콘텐츠 운영

### 11-1. 결과 유형 (억지로 비율을 맞추지 않는다)

| 유형 | 예 |
|---|---|
| 효과 없음 | 시간·비용이 거의 그대로 |
| 기존 방식이 더 빠름 | AI 결과를 고치는 시간 > 원래 작업 시간 |
| 비용 대비 가치 없음 | 유료 구독료 > 절약된 가치 |
| 조건부 | 특정 사람·조건에서만 유용 |
| 실행 실패 | 도구 오류, 과제 수행 불가 |
| 테스트 중단 | 사전에 정한 중단 기준에 도달 |

### 11-2. 원칙
- **제목**: 결과를 정직하게 쓰되 조롱하거나 과장하지 않는다. "…해봤는데, 이번엔 원래 방식이 더 빨랐다"는 가능하다. "AI 쓸모없다"는 쓰지 않는다.
- **본문 필수 요소**: 어디서 실패했나 / 왜 그랬을 가능성이 있나 / **누구나 어떤 조건에서는 다를 수 있나** / 다시 한다면 무엇을 바꿀까
- **연결**: 실패 글에는 반드시 "다음(Next)" 링크나 예고를 둔다. "조건을 바꾸면?"이 인박스로 간다.
- **글이 안 될 만큼 작은 실패**는 Research Log에 남기고, 의미가 있으면 주간 노트에 한 줄로 쓴다.
- 실패 목록 페이지는 자동으로 모인다. 월간 결산에 "이번 달 기대 미달"을 넣는다.

## 12. Weekly / Monthly Layer

채널(이메일, 카톡 등)은 정하지 않았다. **웹 페이지로 먼저 운영**한다.

### 12-1. 주간 노트 (매주 같은 요일, 2~3시간)

| 코너 | 재료 (재활용 원천) | 새로 쓰는 분량 |
|---|---|---|
| 이번 주 바뀐 것 1~2개 | BRIEF, 또는 인박스의 변화 항목 한 줄 판정 | 짧음 |
| 이번 주 직접 확인한 것 | 이번 주 발행 글 요약 + **Research Log의 한두 줄** | 짧음 |
| 해볼 것 하나 | 기존 글의 **"혼자 해보려면" 칸**에서 가져옴 | 거의 없음 |
| 진행 중 실험 | TRACK의 이번 주 기록 | 짧음 |
| 업데이트된 이전 글 | 버전 기록 블록 | 거의 없음 |

→ 매번 새 원고를 쓰는 구조가 아니다. **이번 주 엔진이 만든 결과물을 엮는 편집물**이다.

### 12-2. 월간 결산 (매월 첫 주, 3~4시간)

| 항목 | 재료 |
|---|---|
| 이번 달 실험 목록 | 상태·ID 목록 (자동) |
| 기대 이상 / 기대 이하 | 판정 필드 |
| 측정된 절약 시간 | **실측값만** 합산 (추정치 제외) |
| 비용 변화 | 운영자가 실제로 결제한 도구 |
| 실패·중단 | 실패 목록 |
| 판정 변경·정정 | 버전 기록 블록 |
| 다음 달 추적 계획 | TRACK 일정, 점검 예정 글 |
| 균형 점검 (내부용, 공개하지 않음) | Cluster·카테고리 편중, 수익 주장 비중 |

## 13. Long-term Tracking

### 13-1. TRACK 승격 기준
TEST 결과나 인박스 항목 중 **다음 중 2개 이상**에 해당하면 TRACK으로 승격을 검토한다.
- 주 1회 이상 반복되는 업무다
- 비용이 계속 발생한다 (구독 등)
- 습관이 바뀌어야 효과가 나타난다
- 초기 결과와 장기 결과가 다를 가능성이 크다 (익숙해지면 빨라지거나, 처음만 신기하거나)
- **운영자가 그 기간 동안 실제로 그 일을 한다** (필수 조건)

### 13-2. 기간 선택

| 기간 | 용도 |
|---|---|
| 7일 | 가벼운 습관, 생활 과제 (식단, 메모) |
| **30일 (기본)** | 반복 업무 (업무보고, 리뷰 답글) |
| 90일 | 비용이 드는 도구의 본전 판단 |
| 6개월 | 상시 기록이 아니라 **재방문 체크포인트**로만 ("6개월 뒤 아직 쓰나?") |

### 13-3. TRACK 하나가 만드는 콘텐츠
`시작 글 (설계 공개) → 중간 업데이트 (주간 노트 코너 또는 본문 업데이트) → 최종 글 (측정 결과, 판정) → 90일·6개월 재방문 (버전 기록 또는 짧은 후속)`
→ TRACK 1건은 **글 2~3편 + 주간 노트 4~8회분의 재료**가 된다.

### 13-4. 제한
- **동시 진행 최대 2건**
- TRACK의 최종 주에는 HIGH 난이도 TEST를 배치하지 않는다(4주 시뮬레이션에서 확인한 병목).

## 14. Research Log와 공개 콘텐츠 구분

| 구분 | Research Log (내부) | Published Content (공개) |
|---|---|---|
| 목적 | **무엇을 확인했는가**의 기록 | 독자에게 쓸모 있는 결과 |
| 단위 | 실행 1회 (10분짜리 확인도 포함) | 과제 1개 |
| 기준 | 해봤으면 남긴다 | 선정 규칙과 편집 정책 통과 |
| 공개 | 기본 비공개. 주간 노트에 한두 줄 인용 가능 | 공개 |

**Research Log 한 줄 양식**
`날짜 | 관련 ID 또는 Cluster | 과제 | 도구·버전·요금제 | 한 일 | 걸린 시간 | 결과 한 줄 | 처리: 기사화 후보 / 주간 노트 한 줄 / 기록만 | 증거 위치`

- Research Log 건수는 **공개 실적 숫자로 쓰지 않는다.** 공개 지표는 발행된 글에서만 계산한다(architecture §9).
- 이후 선택지: 로그 일부를 "짧은 확인 기록"으로 공개할 수 있다. 이 경우에도 건수를 과시하지 않는다(나중에 결정).

## 15. Evidence Storage

### 15-1. 보관 구조 (콘텐츠 ID별)

```
evidence/                     ← 공개 사이트와 분리된 개인 저장소 (이 기획 폴더에 넣지 않음)
└─ T-2026-001/
   ├─ conditions.md   과제, 기준선, 성공 기준, 사전 설계, 날짜, 도구·모델·버전·요금제
   ├─ prompts.md      입력한 원본 프롬프트 (순서대로)
   ├─ outputs/        AI 결과물 원본 (텍스트, 파일)
   ├─ screenshots/    화면 캡처 (개인정보 가린 뒤)
   ├─ timelog.csv     작업 단계별 시작·종료 시각
   ├─ cost.md         결제 내역 요약 (영수증 원본은 별도 보관)
   └─ sources.md      출처 URL과 확인일
```

### 15-2. 원칙
- **재현 가능한 수준**으로 남긴다. 나중에 재검증하거나 강의 자료로 쓸 때 같은 조건으로 다시 할 수 있어야 한다.
- **절대 저장·공개하지 않는 것**: 고객·투숙객·거래처 정보, 예약 번호, 연락처, 회사 기밀, 계정 정보, 결제 카드 정보, 동의하지 않은 사람의 얼굴·목소리
- 캡처하기 **전에** 가린다. 가상 또는 각색 데이터를 쓰는 것이 기본이다.
- 공개 범위: 본문에는 대표 스크린샷과 측정표만 싣는다. 원자료는 요청이 있거나 재검증할 때 부분 공개한다.
- 보관 기간과 백업 위치는 운영자가 정한다(결정 사항).

## 16. AI 제작 Workflow (역할 분리)

| 단계 | 사람 (필수) | AI (보조, 적극 활용) |
|---|---|---|
| 인박스 정리 | 선정 판단 (5분 규칙) | 인박스 항목 요약·중복 찾기, 관련 기존 글 찾기 |
| 설계 | 과제, 기준선, 성공·중단 기준 결정 | 설계 체크리스트 점검, 빠진 조건 지적 |
| 실행 | **실제 실행, 시간 측정, 결과 판단** | (실험 대상 AI 자체) |
| 기록 | 원자료 보관 | 시간 로그 계산, 비교표 정리 (사람이 샘플 검산) |
| 자료 조사 | 원출처 최종 확인 | 출처 후보 정리, 공식 문서 위치 찾기 |
| 작성 | **판정, "누구에게 맞나/안 맞나", 1인칭 경험 서술**, 최종 편집 | 표준 틀에 맞춘 초안 구조, 문장 교정, 가독성 |
| 점검 | 사실·개인정보·이해관계 최종 확인 | 체크리스트 대조, 금지 표현 탐지 |
| 연결 | 링크의 "왜" 문장 확정 | 관련 글 후보 제안 |
| 주간·월간 | 코너 선택, 한 줄 판정 | 이번 주 로그·발행 글 모아 초안 편집 |

**넘지 않는 선** (편집 정책 X1~X9 재확인)
- AI는 **1인칭 경험 문장을 쓰지 않는다.** 경험 서술은 운영자가 쓰거나, 운영자의 메모를 교정하는 수준으로만 쓴다.
- AI가 계산한 수치는 사람이 **최소 1개 이상 검산**한다.
- AI가 제시한 출처는 사람이 **직접 열어서** 확인한다.
- 모든 글에 "이 글의 제작에 AI를 쓴 부분"을 한 줄로 적는다.

## 17. 최소 운영 버전 (Minimum Media Engine)

구현 수단은 정하지 않는다. 스프레드시트, 노트 앱, 폴더로 충분하며, 사이트 개발이나 CMS 없이도 운영 준비를 시작할 수 있는 수준이다.

### 17-1. MUST HAVE (오픈 전 필요)

| 요소 | 최소 형태 | 없으면 생기는 문제 |
|---|---|---|
| 콘텐츠 관리표 | ID, 형식, Cluster, 카테고리, 확인 수준, 최초·최종 확인일, Freshness, 다음 점검일, 상태 (§8) | 무엇이 낡았는지, 무엇이 진행 중인지 모른다 |
| 인박스 | 한 곳의 목록 (출처 소스, Cluster, 한 줄 과제) | 매주 "뭘 쓰지?"부터 다시 시작한다 |
| 선정 규칙 | §7 관문 3개 + 우선순위 3개 | 쉬운 글이나 도구 중심 글로 흐른다 |
| 형식별 체크리스트 | TEST, TRACK, BRIEF, GUIDE (CHECK는 첫 CHECK 발행 전까지) | 측정·기록이 빠져서 재측정이 필요해진다 |
| Research Log | 한 줄 양식 (§14) | 확인한 것이 사라지고, 주간 노트 재료가 부족해진다 |
| 증거 폴더 규칙 | ID별 폴더, 개인정보 금지 (§15) | 재검증과 강의 활용이 불가능해진다 |
| 글 끝 연결 | 이유 문장이 있는 링크 최대 3개 (§2) | 한 편 읽고 끝나는 블로그가 된다 |
| 버전 기록 블록 | 모든 글 하단 (§10) | 조용히 덮어쓰게 된다 |
| 주간 노트 | 웹 페이지 1개 / 주 (§12-1) | 재방문 슬롯이 없다 |
| 방법론 페이지 | 40번 글 | 신뢰의 기준점이 없다 |
| 과제 허브 | 4개: 회의·보고 / 업무 글쓰기 / AI 답 확인하기 / 가게 응대·홍보(임시 통합). 구조는 site-ia §8 | 과제 중심이라는 인상이 흐려진다 |
| 진행 중 TRACK 1건 | 오픈 2~3주 전 시작 (9번) | 오픈 시점에 "다음 결과"가 없다 |

### 17-2. SHOULD HAVE (운영 1~3개월 안)

- 월간 결산 (첫 달 말부터)
- 이벤트 트리거 점검 루틴과 월 업데이트 예산 (§9)
- 실패 목록 페이지, 정정 로그 페이지 (처음에는 수동 목록)
- 나머지 Cluster 허브, 운영자 업무 소스 기반의 C3·C7 백로그 보강
- 첫 CHECK 체크리스트 (톤·저격 점검 포함)
- 소규모 인터뷰 라운드 (§18)

### 17-3. LATER (트래픽·콘텐츠가 쌓인 뒤)

| 요소 | 나중으로 미루는 이유 |
|---|---|
| 연구 기록 페이지의 자동 통계 | 초기에는 숫자가 작아 오히려 약점이 드러난다. 수동 목록으로 충분하다 |
| 판정 변경 로그 (사이트 전체) | 재검증이 쌓여야 의미가 생긴다 |
| 독자 검증 요청 시스템 | 독자가 생긴 뒤 (오픈 3개월 이후 검토) |
| 검색 유입 질문 분석 | 데이터가 쌓인 뒤 |
| 과제 인덱스 UI, Freshness 자동 표시 | 사이트 개발 단계에서 |
| 주간 노트 발송 채널 (이메일, 카톡) | Phase 2 P3 검증 후 |
| 회원 개인화, 저장 기능 | 방문 패턴이 확인된 뒤 (Phase 5 회원 구조) |
| 추천 알고리즘 | 명시적인 이유 링크(§2)로 충분하다. 콘텐츠가 수백 편이 된 뒤 검토 |
| Research Log 일부 공개 | 운영이 안정된 뒤 선택 |

## 18. Phase 2 인터뷰와의 관계

대규모 인터뷰(15~20명)는 현재 우선순위가 아니다. **인터뷰는 사이트 오픈의 선행조건이 아니다.** 남겨둔 가설 세 개는 폐기하지 않고, **운영 중에 관찰되는 독자 행동 + 소규모 인터뷰**로 검증한다.

| 가설 | 운영 중 관찰할 신호 (사이트 데이터) | 소규모 인터뷰 (오픈 후 1~3개월, 각 2~4명) | 결과를 반영할 곳 |
|---|---|---|---|
| **P1 복귀 계기** (문제 / 사람 / 앱) | 유입 경로(검색, 공유, 직접), 입구 글 종류(Journey J1~J6 중 어디로 들어오나) | 공유받아 들어온 독자, 교육 후 들어온 독자에게 "이 글을 어떻게 보게 됐는지", "그 뒤 AI를 다시 써봤는지" (인터뷰 가이드 C3 재사용) | Journey 우선순위, Source 우선순위 |
| **P3 정기 수신 습관** | 주간 노트 페이지의 재방문 여부, 요일 패턴 | 재방문 독자와 한 번만 온 독자에게 "지난 7일 동안 챙겨본 정보 채널" (가이드 C4 재사용) | **주간 노트 발송 채널 결정** (LATER 항목) |
| **P5 기관 교육** | 기관·기업에서 온 문의, 소개 페이지 방문 | 기관 교육 담당자 2~3명 (Buyer Track 가이드 재사용, 영업하지 않음) | 교육 연결 방식, 연구 기록 페이지 설계 |

- 인터뷰 기록은 기존 [phase2-interview-template.md](../research/phase2-interview-template.md)를 그대로 쓴다. 가상 발언을 만들지 않는 원칙도 그대로다.
- P2(교육 후 이탈), P4(경제 효과 동기)는 운영자가 강의를 하게 되거나 수익 주장 CHECK의 반응이 쌓이면 다시 꺼낸다.
