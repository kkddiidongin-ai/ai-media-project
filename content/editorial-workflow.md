# 편집 운영 Workflow (체크리스트와 양식)

작성일: 2026-09-29 · 상태: **초안. 운영 첫 8주 동안 실제로 써보고 수정**
규칙의 근거: [../strategy/media-engine.md](../strategy/media-engine.md) (엔진 규칙) · 글 표준 틀과 라벨: [../strategy/content-media-architecture.md](../strategy/content-media-architecture.md) §6~§7 · 원칙: [../strategy/editorial-policy.md](../strategy/editorial-policy.md)

> 이 문서는 **매주 실제로 손에 쥐고 쓰는 양식**만 담는다. 규칙의 이유는 media-engine.md에 있으므로 반복하지 않는다.
> 도구는 정하지 않았다. 스프레드시트, 노트 앱, 폴더로 운영할 수 있다.

## 1. 주간 운영 리듬 (예시, 주 15~22시간 기준)

| 요일 (예시) | 할 일 | 시간 |
|---|---|---|
| 1일차 | 인박스 정리 → **5분 선정 규칙**으로 이번 주 2편 결정, 점검 필요 목록 확인 | 30~45분 |
| 1~3일차 | 직접 실행형 1편: 설계 → 실행 (Research Log·timelog를 **실행하면서** 기록) | 4~7시간 |
| 2~4일차 | 가벼운 1편 (BRIEF 또는 GUIDE) | 1~5시간 |
| 매일 | 진행 중 TRACK 기록 | 5~20분 |
| 4~5일차 | 작성, 발행 전 점검, 발행, 연결 | 3~5시간 |
| 5일차 | 주간 노트 편집·발행 | 2~3시간 |
| 수시 | 짧은 확인은 Research Log에만 기록 | 주 1~2시간 |
| 매월 첫 주 | 월간 결산 + Freshness 점검 (업데이트 예산 4~6시간 안에서) | 3~4시간 + 4~6시간 |

## 2. 콘텐츠 관리표 (열 구성)

```
ID | 가제 | 형식 | Cluster | 카테고리 | 확인 수준 | 상태 | 최초 확인일 | 최종 확인일 | Freshness(FAST/MEDIUM/SLOW) | 다음 점검일 | 판정 | 효과 태그 | 연결(배경/비교/다음/추적 ID) | 남은 질문 | 증거 폴더 | 비고
```

- 상태: 아이디어 / 진행 중 / 발행 / 추적 중 / 점검 필요 / 보관
- ID 예: `T-2026-001` (T=TEST, R=TRACK, C=CHECK, B=BRIEF, G=GUIDE, W=주간 노트, M=월간 결산)

## 3. 인박스 양식

```
날짜 | 소스(업무/남은 질문/실패/재검증/서비스 변화/주장/생활/요금·정책/교육/커뮤니티/독자/새 도구) | 관련 Cluster | 한 줄 과제 ("누가, 어떤 일을 할 때, 무엇이 문제") | 관련 기존 ID | 메모
```

## 4. 선정 기록 (주 1회, 5분)

```
후보 ID | 관문1 과제 문장 O/X | 관문2 확인 가능 O/X (확인 수준) | 관문3 안전 O/X | A 연결 | B 출처(업무·생활) | C 크기(이번 주 슬롯) | 결정: 이번 주 / 다음 주 / 인박스 유지
```

## 5. 형식별 체크리스트

### 5-1. TEST
- [ ] 과제 문장 1줄
- [ ] **사전 기록** (`conditions.md`): 과제, 기준선 방법, 성공 기준, 사용할 자료(가상·각색 여부), 도구·버전·요금제, 날짜
- [ ] 기준선 측정 (AI 없이 걸린 시간 / 과거 기록 / 추정이면 "추정" 표시)
- [ ] 실행하면서 timelog 기록, 프롬프트 원본 저장, 결과 원본 저장
- [ ] 스크린샷 (찍기 **전에** 개인정보 가리기)
- [ ] 비용 기록 (결제 여부)
- [ ] 실패·재시도·사람이 고친 부분 기록
- [ ] Research Log에 실행 기록 추가
- [ ] 표준 틀 10단계로 작성
- [ ] 판정 (쓸 만함 / 조건부 / 비추천), "누구에게 맞나 / 안 맞나", "다시 쓸 것인가"
- [ ] "혼자 해보려면" (무료로 따라 할 최소 단계)
- [ ] 남은 질문 1~3줄 → 인박스
- [ ] 발행 전 공통 점검 (§6)

### 5-2. TRACK
- [ ] 승격 기준 확인 (media-engine §13-1, 2개 이상 + "운영자가 실제로 그 일을 한다")
- [ ] 동시 진행 TRACK 수 확인 (최대 2건)
- [ ] **사전 공개 설계**: 기간(7/30/90일), 기록 항목, 기록 시점, **중단 기준**, 성공 기준
- [ ] 기록표 준비 (§9)
- [ ] 시작 글 발행 (상태: 추적 중, 다음 업데이트 날짜)
- [ ] 매일·매주 기록 (빠진 날도 "기록 없음"으로 남김)
- [ ] 중간 업데이트: 주간 노트 코너 또는 본문 업데이트
- [ ] 최종 글: 측정 결과, 판정, 기대와 달랐던 점, 남은 질문
- [ ] 90일·6개월 재방문 일정을 관리표에 입력

### 5-3. CHECK
- [ ] 주장 원문과 원출처 URL, 확인일 저장 (캡처)
- [ ] 주장 조건 정리: 기간, 매출/순이익 구분, 비용 포함 여부, 선행 자산(팔로워 등), 강의·제휴 수익 혼입 가능성
- [ ] 실행 가능 여부 판단 → 실행(TEST 방식) / **실험 안 함 (이유 기록)**
- [ ] 결과는 매출, 순이익, 도구비, 광고비, 투입 시간을 구분해서 기록. 모르면 "미검증 주장"
- [ ] **"누구에게는 통할 수 있는지"** 칸 작성 (냉소 방지)
- [ ] 특정 판매자·개인 저격 여부 점검 (공개된 주장 구조만 다룸)
- [ ] 수익 주장이면 제목에 수익 숫자 금지, 이번 달 수익 주장 CHECK 수 확인 (월 1편 이하)
- [ ] 발행 전 공통 점검 (§6)

### 5-4. BRIEF
- [ ] **"어느 Cluster의 과제에 영향을 주나?"** → 없으면 주간 노트 한 줄 또는 버림
- [ ] 공식 발표 원문 확인 (URL, 확인일)
- [ ] 직접 사용 30~60분 (Research Log 기록). 못 써봤으면 확인 수준 "출처 확인"으로 표시하고 판정하지 않음
- [ ] 무엇이 / 왜 / 나에게 / 써볼까·넘길까 (800~1,500자)
- [ ] 영향을 받는 기존 글이 있으면 그 글을 "점검 필요"로 전환
- [ ] Freshness: FAST (30~60일)

### 5-5. GUIDE
- [ ] 근거로 쓸 사이트 안의 글 ID 목록
- [ ] 외부 공식 출처와 확인일
- [ ] 확인 수준 표시 (사이트 안 실험 근거가 없으면 "출처 확인")
- [ ] 실천 기준을 3~5개로 정리
- [ ] Freshness: SLOW (단, 요금·정책 내용이 있으면 해당 부분은 FAST로 따로 관리)

## 6. 발행 전 공통 점검

- [ ] 확인 수준 (실측 / 직접 사용 / 출처 확인) 표시
- [ ] 확인일, 도구·버전·요금제
- [ ] 이해관계 (제휴 없음 / 제휴 포함 / 협찬·무상 제공)
- [ ] "이 글의 제작에 AI를 쓴 부분" 한 줄
- [ ] 개인정보·고객정보·회사 기밀 없음 (스크린샷 포함), 가상·각색 데이터 여부 명시
- [ ] 금지 표현 없음 (editorial-policy §7)
- [ ] 1인칭 경험 문장은 운영자가 쓴 것인지 확인
- [ ] AI가 계산한 수치 1개 이상 검산, AI가 제시한 출처 직접 열어봄
- [ ] 글 끝 연결 최대 3개, 각각 "왜 다음 글인가" 한 문장
- [ ] 버전 기록 블록 (최초 확인)
- [ ] 관리표 입력: 상태, Freshness, 다음 점검일, 남은 질문
- [ ] Cluster 허브에 추가

## 7. 월 1회 Freshness 점검

```
ID | Freshness | 다음 점검일 | 이벤트(가격/모델/UI/정책/재현 실패/종료) | 조치(확인만/부분 업데이트/재검증/보관) | 소요 시간 | 판정 변경 여부 | 다음 점검일
```

- 이번 달 업데이트 예산: 4~6시간. 넘치면 "재검증 필요" 표시만 하고 다음 달로 넘긴다.
- 우선순위: Launch·Journey 입구 글 → 판정 변경 가능성이 큰 이벤트 → Cluster 허브에 걸린 글 → 나머지

- YYYY-MM-DD  재검증          재실행 결과 요약         판정: ○○ → ○○
- YYYY-MM-DD  보관            사유, 대체 글 링크

## 9. TRACK 기록표

```
일차 | 날짜 | 한 일 | AI 사용 여부 | 걸린 시간(분) | 사람이 고친 정도(없음/일부/대부분) | 비용 | 메모(막힌 점, 달라진 점)
```

## 10. Research Log

```
날짜 | 관련 ID 또는 Cluster | 과제 | 도구·버전·요금제 | 한 일 | 걸린 시간 | 결과 한 줄 | 처리(기사화 후보/주간 노트 한 줄/기록만) | 증거 위치
```

## 12. 결과별 처리 흐름

| 실행 결과 | 처리 |
|---|---|
| 의미 있는 결과 (성공이든 실패든) | 글로 발행. 실패면 media-engine §11-2 원칙 적용 |
| 작지만 흥미로운 결과 | 주간 노트 한 줄 + Research Log |
| 의미 없음 | Research Log만 |
| 조건을 바꾸면 달라질 것 같음 | 인박스에 "남은 질문"으로 추가 |
| 반복 업무·비용 발생·장기 효과가 의심됨 | TRACK 승격 검토 |

## 13. 주간 노트 양식

```
# 주간 노트 ○호 (YYYY-MM-DD)

## 이번 주 바뀐 것
- (BRIEF 링크 또는 한 줄 판정 + 확인 수준) / 없으면 이 코너 생략

## 이번 주 직접 확인한 것
- 발행 글: (제목 + 판정 한 줄 + 링크)
- 짧은 확인: (Research Log에서 한두 줄)

## 해볼 것 하나
- (기존 글의 "혼자 해보려면"에서 가져옴 + 링크)

## 진행 중 실험
- (TRACK 이름, ○일째, 이번 주 기록 요약, 다음 업데이트 날짜)

## 업데이트된 이전 글
- (버전 기록에서: 무엇이 바뀌었나)
```

## 14. 월간 결산 양식

```
# ○월 결산

## 이번 달 확인한 것 (목록)
## 기대 이상 / 기대 이하
## 측정된 절약 시간 (실측만, 글 링크와 함께)
## 비용 변화 (운영자가 결제한 도구)
## 실패·중단
## 판정 변경·정정
## 다음 달 추적·점검 예정

(내부 메모, 공개하지 않음) Cluster·카테고리 편중 / 수익 주장 비중 / 업데이트 예산 사용량 / 실제 주간 작업 시간
```
